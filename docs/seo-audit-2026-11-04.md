**Copes Gidi — SEO audit, 4 November 2026**

The site has a sound foundation for a Latvian fishing-guide directory: useful individual profiles, published prices, source attribution, crawlable listings, and a shallow link structure. The immediate priorities are to align the production hostname and canonical URLs, control filtered URLs, improve search snippets, and make the main pages more explicit about their purpose. The largest content opportunity is a small set of useful fishing and location landing pages backed by the existing catalog.

This is an analysis and implementation brief. Application code and deployment settings have not been changed.

**Scope, evidence, and limits**

Audited the repository at commit `0615144`, fetched the live robots file and sitemap, and crawled the production `www` equivalents of all 63 sitemap URLs. Also checked the privacy page, three filter variants, four nonexistent URLs, hostname/protocol variants, trailing-slash behavior, a Googlebot-user-agent request, initial JavaScript/CSS assets for four representative pages, eight preloaded fonts, and 15 guide website destinations. Inspected the installed Next.js 16.4.3 metadata and rendering documentation.

The sitemap contains 17 guide profiles, 37 trip pages, five regions, and four core pages. The privacy page is an additional public page. Page-level results are in [the CSV inventory](seo-page-inventory-2026-11-04.csv); supporting measurements and probe results are in [the evidence JSON](seo-evidence-2026-11-04.json).

These are HTTP, HTML, asset, source-code, and public-search observations. Search Console, analytics reports, server logs, backlink databases, and keyword-volume tools were not available. The browser automation host was unavailable, and PageSpeed Insights returned HTTP 429 with an API quota error. Consequently this report does not claim measured Core Web Vitals, Lighthouse scores, rendered mobile usability results, rankings, organic traffic, backlink counts, or Google-selected canonical URLs. A spoofed Googlebot user agent checks the response only; it is not Google's URL Inspection test.

**A1. Production hostname and canonical URLs**

The live apex homepage returns `308` to `https://www.copesgidi.lv/`; the apex `/gidi` URL does the same. HTTP variants redirect toward HTTPS, and `/gidi/` redirects to `/gidi`. These are useful permanent redirects.

However, `site.url` and `.env.example` use `https://copesgidi.lv`. The live sitemap lists all 63 URLs on that apex hostname, and robots advertises the apex sitemap. No sitemap page includes `rel="canonical"`. `metadataBase` resolves URL-valued metadata when supplied; it does not create canonical links by itself.

Keep the existing `www` destination unless there is a business reason to migrate it. Update the production origin in code and the actual production environment, then generate per-route `alternates.canonical` and `openGraph.url`. Use a shared metadata helper if useful, but pass the actual path for every page. A root-layout canonical of `/` inherited across all pages would introduce a serious new error.

For dynamic routes, derive the path from the validated guide/trip/region slug. Normalize the configured origin to avoid trailing-slash mistakes. Sitemap entries should be final, canonical, indexable URLs. `/privatums` is absent from the current sitemap but is linked sitewide; adding it is optional and low priority. Missing sitemap `priority` or `changefreq` values are not defects. Add accurate `lastModified` values only when meaningful content changes, rather than stamping the current time on every build. [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

Implementation locations: [site configuration](../src/lib/site.ts), [layout](../src/app/layout.tsx), [robots](../src/app/robots.ts), [sitemap](../src/app/sitemap.ts), all page metadata exports, and production environment variables.

**A2. Filter URLs and indexable landing pages**

These live requests return 200 with the same initial catalog text, title, and description as their base listing:

- `/braucieni?suga=lasis`
- `/braucieni?suga=not-a-species`
- `/gidi?regions=kurzeme`

Filters run through client-side `useSearchParams`; their Suspense fallback contains the entire catalog. This is good for discovering all profiles and trips. It also means a fish-specific URL does not provide a distinct fish-specific initial search document. After hydration, an unknown species produces an empty result set. Robots currently allows these URL variants, and neither canonical nor noindex rules distinguish them.

For the current site size, uncontrolled variants are an avoidable duplication and relevance issue; an actual crawl-budget problem has not been demonstrated.

Recommended policy:

| URL category | Intended behavior |
| --- | --- |
| `/gidi`, `/braucieni`, real profiles/trips/regions | Indexable, self-canonical, linked and in sitemap as appropriate |
| Sorting-only variations such as `?kartot=cena` | Consolidate to the relevant unsorted canonical URL |
| Uncurated multi-filter combinations | Exclude from indexing with a deliberate robots-meta policy; omit from sitemap |
| Valuable species/type searches | Create stable landing pages with unique server-rendered introductions, relevant results, and self-canonicals |
| Invalid filter values | Validate/normalize them; avoid treating arbitrary values as indexable landing pages |

For a noindex policy, keep URLs crawlable so the directive can be read. Do not simultaneously add robots blocking and expect the page's noindex/canonical tags to be processed. Canonicalization is appropriate for equivalent documents; it should not collapse genuinely useful distinct landing pages into the homepage. Keep base catalogs linking to every profile/trip even if utility facets are noindexed. [Google faceted-navigation guidance](https://developers.google.com/crawling/docs/faceted-navigation), [robots-meta requirements](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag).

Implementation locations: [explorers](../src/components/explorers.tsx), [trip listing](../src/app/braucieni/page.tsx), [guide listing](../src/app/gidi/page.tsx), [footer](../src/components/site-footer.tsx), and homepage species/type links. Read the installed Cache Components and `searchParams` documentation before changing server rendering; retain useful HTML in the cached shell.

**A3–A4. Titles, snippets, and search intent**

All 17 guide titles are 81–129 characters long. Their descriptions are 284–484 characters because metadata reuses the full profile summary. Across the entire sitemap, 20 descriptions exceed 170 characters. These lengths are editorial diagnostics, not Google limits or penalties: display depends on width, query, and device, and Google may choose different text. The issue is that full biographies push identifying service/location information into crowded snippets. [Google title guidance](https://developers.google.com/search/docs/appearance/title-link).

Examples of the desired direction; final wording should match each guide's confirmed coverage:

| Page | Suggested title | Suggested H1 or adjacent visible descriptor |
| --- | --- | --- |
| `/` | `Makšķerēšanas gidi Latvijā — cenas un braucieni · Copes Gidi` | Keep the brand slogan; add `Makšķerēšanas gidi un braucieni Latvijā` visibly beside it |
| `/gidi` | `Makšķerēšanas gidi Latvijā · Copes Gidi` | `Makšķerēšanas gidi Latvijā` |
| `/braucieni` | `Makšķerēšanas braucieni ar gidu Latvijā · Copes Gidi` | `Makšķerēšanas braucieni ar gidu Latvijā` |
| `/gidi/imants-tiltins` | `Imants Tiltiņš — cope ar gidu Pierīgā · Copes Gidi` | Keep the person's name and visible service summary |
| `/gidi/kaspars-holms` | `Kaspars Holms — zandartu cope ar gidu · Copes Gidi` | Keep the person's name and visible service summary |
| `/regioni/riga` | `Makšķerēšana ar gidu Rīgā un Jūrmalā · Copes Gidi` | `Makšķerēšana ar gidu Rīgā un Jūrmalā` |

Suggested homepage description: `Salīdzini makšķerēšanas gidus un braucienus Latvijā: publicētās cenas, ūdeņus, laivas un aprīkojumu. Sazinies tieši ar izvēlēto gidu.`

Suggested Imants Tiltiņš description: `Imants Tiltiņš: līdaku, zandartu un asaru cope Pierīgā, samu cope Daugavā un ziemas braucieni. Publicētās cenas, laiva un tiešie kontakti.`

Aim for compact, distinct summaries, often around 130–160 characters where natural. Retain the complete biographies in page content. Do not make unsupported claims such as “best”, guaranteed catches, live availability, or verified final prices.

The homepage H1 is the slogan “Cope bez pasakām”; `/gidi` says “Gidi”, and `/braucieni` says “Visi braucieni”. Their metadata is relevant, so this is not an absence of all topical signals. Clearer visible headings would help visitors and make the page purpose less ambiguous. Do not simply add hidden keywords. Several profile/trip sections use paragraph-based `Eyebrow` labels before H3 headings; real H2 section headings would improve document navigation. This is a secondary semantic/usability improvement.

**A5. Editorial accuracy and seasonal advice**

`src/data/species.ts` marks October and November as the best months for salmon and sea trout, and the homepage presents one national calendar with a general reminder about restrictions. That is too broad for trip planning: legal access, retention, method, and water-specific restrictions differ. The current national rules include autumn restrictions in named rivers and salmon/sea-trout retention rules. This does not establish that every autumn trip is prohibited; it establishes that the present undifferentiated recommendation needs qualification. [Current national rules](https://likumi.lv/ta/id/279205-makskeresanas-vezosanas-un-zemudens-medibu-noteikumi).

Have a knowledgeable editor review the calendar against current water-specific rules. Distinguish expected fish activity from permitted fishing, link directly to the relevant official sources, and show a real review date. Keep any advice about cards, exemptions, licenses, ice safety, and restricted species subject to the same review. This matters for usefulness and trust; no search penalty was observed or inferred.

**A7. Performance: measured payloads and source-based risks**

| Representative live page | Decoded HTML bytes | Initial linked JavaScript, decoded | JavaScript gzip estimate |
| --- | ---: | ---: | ---: |
| Homepage | 443,858 | 607,329 | 188,772 |
| `/braucieni` | 378,147 | 718,567 | 219,984 |
| `/gidi` | 140,215 | 718,567 | 219,984 |
| `/regioni/riga` | 414,054 | 604,073 | 187,458 |

These are fetched resource sizes, deduplicated by URL per page. Gzip estimates were calculated locally; they are not browser network transfer measurements and exclude dynamically requested assets and later prefetches. The shared CSS is 55,231 decoded bytes. The homepage response preloads eight WOFF2 files totaling 255,696 bytes. Fonts are additional to the table, and WOFF2 is already compressed.

Confirmed sources of avoidable work:

- The loader overlays the first visit for a CSS sequence ending after approximately 2.6 seconds. Remove this artificial wait. It is a user-perceived delay, not a measured 2.6-second LCP regression.
- Three font families and two Space Mono weights are configured globally, with Latin and Latin Extended subsets. Reduce globally critical font loads, retain Latvian glyph coverage, and measure before dropping weights or preloads.
- The catalog client chunk is 111,488 decoded bytes and contains full guide sources, claims, and company data. Filters/cards do not need all profile details. Pass a compact list projection or move the relevant filtering/rendering work to the server, then verify the extra data disappears from the browser bundle.
- Large repeated inline SVG scenes contribute to HTML/DOM size. `/braucieni` has 41 SVGs and about 2,060 parsed elements. Consider reusable optimized visual assets or simpler repeated artwork; preserve HTML text and trip links.
- Scroll effects repeatedly query the DOM and read geometry. Profile on mobile before changing them; IntersectionObserver and cached element references are plausible improvements, not measured fixes yet.
- Reveal CSS hides content when `data-js` is set until a client effect marks it visible. Add a failure-safe visible state if hydration fails; do not assert this content is unindexable solely because it animates.

Measure cold first visits and repeat visits on representative mobile devices, including a long catalog and detail page. Verify LCP ≤2.5 seconds, INP ≤200 ms, and CLS ≤0.1 at the 75th percentile when field data becomes available. Lab tests help identify causes; passing them does not establish field performance. [Web Vitals definitions](https://web.dev/articles/vitals).

**A8. Regional content and coverage**

The five region descriptions contain only 18–32 words each; the rest of these pages is mostly inventory and shared interface text. There is no required SEO word count. The gap is missing practical local information that would help a visitor choose a trip.

| Region | Guides assigned to region | Trips assigned to region | Original region-description words |
| --- | ---: | ---: | ---: |
| Kurzeme | 2 | 5 | 32 |
| Vidzeme | 1 | 6 | 18 |
| Latgale | 2 | 3 | 19 |
| Zemgale and Sēlija | 1 | 2 | 19 |
| Rīga and Jūrmala | 8 | 17 | 25 |

Three guides and four trips have an empty region deliberately used as an unspecified/nationwide fallback. These are visible in the main catalogs but disappear when a specific region is selected. The single `guide.region` field also mixes a base location with service coverage: LV GROUP is based in Rīga but has a Vidzeme-assigned trip that also names Dagda lakes. Its guide card is absent from the Vidzeme guide section despite that trip appearing there.

Separate base location, verified service regions, and unspecified coverage. Include an appropriate guide where a supported trip is offered, without inventing coverage for nationwide/unknown entries. Consider multiple service regions on a trip that genuinely spans them.

For each region add useful, sourced material about typical meeting areas, target species and methods, realistic travel logistics, price basis, included equipment, seasonal limitations, beginner suitability, and which listed guide fits which trip. Put actual comparison and planning information before repetitive catalog cards. Start with Rīga because it already has the largest inventory; this is a supply-based priority, not a verified keyword-volume finding.

**A9. Structured data and entity clarity**

No JSON-LD was found. Recommended markup should describe the actual directory and its content:

| Content | Appropriate starting model | Important constraint |
| --- | --- | --- |
| Homepage | `WebSite` and a truthful publisher `Organization` | Stable `@id`, canonical URL, real name; only real publisher identity/logo/profiles |
| Profile/trip navigation | `BreadcrumbList` | Match visible navigation and valid destination URLs |
| Listings/regions | `CollectionPage` / `ItemList` | Use actual items shown; generic markup does not promise a carousel |
| Guide profile | `ProfilePage` with `Person` or `Organization` as appropriate | A guide team and a named person are different entities |
| Trip detail | `Service`, provider, area served, and suitable offer data if accurately supported | Copes Gidi is the publisher, not the operator or booking seller |

Add visible breadcrumbs including the current page, then match them in JSON-LD. Existing profile/trip navigation omits the current page and uses a region as an intermediate navigation link; choose a coherent visible path such as home → guides → named guide or home → trips → named trip.

Do not add fabricated addresses, coordinates, aggregate ratings, review counts, “in stock” availability, or platform-owned LocalBusiness information for independently operated guides. A generic Service or ProfilePage schema is not a promise of a Google rich result. Validate supported types with Rich Results Test and broader schema with a schema validator. [WebSite/site-name guidance](https://developers.google.com/search/docs/appearance/site-names), [breadcrumb guidance](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb), [structured-data introduction](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data).

FAQ content is useful for visitors, but FAQ rich results are not a reason to prioritize FAQPage JSON-LD: Google's current documentation records that the feature stopped appearing on 7 May 2026. [Google's documentation changelog](https://developers.google.com/search/updates).

**A10. Trust, differentiation, and images**

The sourced profiles, explicit self-claim labels, public check dates, transparent price bases, and statement that the guides are independent are strengths. Preserve these distinctions. Source attribution alone is not the whole value proposition; useful comparison and editorial judgment make the directory worth visiting alongside the guides' own sites. [Google helpful-content guidance](https://developers.google.com/search/docs/fundamentals/creating-helpful-content).

Add a concise publisher/About page identifying who maintains Copes Gidi, what qualifies a listing, how sources and prices are checked, how ordering works, and how corrections are handled. Explain that the present catalog order prioritizes visible recent public activity; do not imply it is an endorsement or quality ranking. Show source/verification dates accurately without refreshing them automatically.

Trip cards and trip hero areas currently use decorative scene illustrations. The trip listing contains no `<img>` elements; guide logos are available elsewhere. Authentic, permissioned photos of guides, boats, equipment, and meeting areas would improve trip evaluation and create useful image assets. Use descriptive alt text for meaningful photos, fixed aspect ratios, appropriate sizes, and optimized image delivery. Decorative scenes can remain hidden from assistive technology. Do not reuse an illustration or stock image as evidence of a real guide, place, or catch.

Fifteen guide website links were checked: fourteen finished with HTTP 200; `predatorfishinglv.com` could not be verified because curl's local certificate-chain validation failed. Treat that as an unresolved environment/destination compatibility check, not proof of a broken website. One guide destination uses HTTP (`uac.lv`); investigate a valid HTTPS equivalent before changing it. This check did not validate all 97 distinct profile-source URLs or confirm every external page's factual contents.

**A6. Measurement and operational controls**

Vercel Analytics is installed, but the repository does not emit explicit conversion events for guide phone, WhatsApp, email, or website links. Their absence in source does not establish which dashboards or external tracking may already be configured. The practical success metric for this directory is a qualified outbound contact, not an on-site booking payment.

Use an existing Search Console property if one is configured; otherwise verify a domain property, submit the corrected sitemap, and inspect one URL of each template. Check the selected canonical, crawlability, indexing reason, and rendered content. DNS verification can exist without a verification token in the repository. [Search Console guidance](https://developers.google.com/search/docs/monitor-debug/search-console-start).

Measure contact-click type, guide identifier and originating page without storing message text, phone numbers or email addresses in event payloads. Measure filters with zero results and successful guide-application submission. Confirm analytics capabilities and the site's privacy wording before deploying event changes.

| Metric | Baseline required | Review |
| --- | --- | --- |
| Intended canonical pages indexed, with exclusion reasons | Search Console indexing + URL Inspection | After release and then weekly initially |
| Non-brand clicks, impressions, CTR and position by page/query | Search Console, split by country/device | Compare similar periods; account for seasonality |
| Guide contact-click rate from organic entrances | Analytics events + acquisition attribution where available | Weekly after validation |

Preview deployments need a separate verification: the application robots function allows crawling in every environment, but Vercel may supply preview protection or `X-Robots-Tag` headers. No preview URL was supplied, so preview indexability is unresolved. Verify an actual preview response and prevent previews from becoming alternate indexed copies. Do not accidentally apply a preview noindex rule to production.

Low-priority maintenance: give the privacy page a suitable description instead of inheriting the marketing description; add an Open Graph image and `summary_large_image` card for homepage and useful detail pages; keep favicon assets crawlable; update README's obsolete claim that all guides are fictional and its obsolete route/form descriptions.

**Suggested delivery sequence**

1. First release: A1–A4 plus calendar review and measurement baseline. Validate the final hostname, every page canonical, metadata uniqueness, filter policy, and 404 behavior in production.
2. Second release: remove the loader, reduce the font/data payload, add truthful publisher/breadcrumb markup, and publish the About/methodology information. Test representative mobile pages and contact events.
3. Content release: expand Rīga and the other existing regions, repair coverage filtering, then publish two or three selected species/type pages with meaningful comparisons and contextual links.
4. Following weeks: review Search Console and contact outcomes, correct low-value pages and zero-result journeys, and expand only where inventory and demand support it.

Acceptance is not a promised ranking or traffic increase. It is a consistent crawl/indexing setup, useful distinct landing pages, faster first visits, accurate information, and observable guide-contact outcomes.
